# CONTRACT: app-hosting

Hosted apps are untrusted: built by the code factory or third-party, kept in the apps repository, one folder each. Core and add-ons are the trusted zone ([services/CONTRACT.md](../../services/CONTRACT.md)) and are unaffected by anything here except the cluster-wide policy objects. How to write one and turn it on: [docs/add-a-hosted-app.md](../../docs/add-a-hosted-app.md).

App hosting is an optional core component, **off by default**. An env turns it on with one line in `envs/<env>/flux/platform-configs/kustomization.yaml`, the file where it turns on the apps backup server:

```yaml
components:
  - ../../../../core/platform/app-hosting
```

Without that line the env renders none of this: no App CRD, no app admission policies or bindings, no `app-derive` or `app-priority` policy, no Kyverno role, no PriorityClass `hosted-app`, and no `wildcard-apps` certificate or TLSStore entry. An env that lists apps with the switch off fails `ci/checks/env-schema`. The switch is a kustomize Component, not a directory under `resources:`, because it adds to an object platform-configs already holds: TLSStore `default` (the apps wildcard). `pvc-backup`'s `privileged-movers` marks an `app-` namespace only once its credential is registered in core itself, on or off ([platform/backups/CONTRACT.md](../backups/CONTRACT.md)).

## Offers

- **The app file.** Every app folder `<name>/` in the apps repository holds one `app.yaml`, an `App` (`hosting.jarvis.io/v1alpha1`, CRD in `crd/app-crd.yaml`). It is the whole definition of the app, per-env differences included. Nothing of an app deploys without a valid one.

  | Field | Required | Default | Meaning |
  | --- | --- | --- | --- |
  | `metadata.name` | yes | | The app's name: its folder name, a DNS label of at most 59 characters. Its namespace is `app-<name>`. |
  | `spec.network.web` | no | no web address | The web address `https://<name>.apps.<dns suffix>` on 443, TLS from core's wildcard. `port`: the plain-HTTP container port Traefik reaches. `healthPath`: what the uptime check requests, starting with `/` (default `/`); healthy is any answer but a 5xx. No app-chosen external port, no app TLS. |
  | `spec.network.ports` | no | `[]` | LAN ports, each a LoadBalancer port: `listen` (on the LoadBalancer), `target` (the container port), `protocol` (`TCP` or `UDP`). Each needs the env's `lan-port <listen>/<protocol>` line. No cluster-internal entries: the namespace reaches itself, and other apps reach it through `callers`. |
  | `spec.network.egress.internet` | no | `false` | Any port and protocol to the internet; never the LAN or the cluster. |
  | `spec.network.egress.lan` | no | `[]` | LAN targets by name, each needing the env's `lan-target` lines, or exactly `[all]` (`all` is reserved), needing `lan-all`. |
  | `spec.network.egress.apps` | no | `[]` | Apps this app calls, at `<service>.app-<other>.svc`. |
  | `spec.network.callers` | no | `[]` | Apps that may call this app, on any port. |
  | `spec.volumes` | yes (may be `[]`) | | Each PVC the app keeps: `name` and `backup: true` or `false`. |
  | `spec.resources` | no | `cpu: 500m`, `memory: 512Mi` | The namespace's total requests and limits (its ResourceQuota). |
  | `spec.risky` | no | all off | Asks for `privileged`, `root`, `hostNetwork`, `hostPath` (booleans) or `hostnames` (custom hostnames outside `.apps`). Each needs the env's exception line. |
  | `spec.envs.<env>` | no | | Per-env overrides of `network.egress.internet` and `resources`. |

  Every network field defaults closed: an App with no `network` has no web address, no LAN port, no egress beyond cluster DNS and no caller. App-to-app traffic flows only when the caller lists the callee under `egress.apps` and the callee lists the caller under `callers`. The API server refuses an App that breaks the schema. `tools/app-check` also refuses unknown keys, which the API server would drop unread. Kubernetes probes stay in the app's `deploy/`.
- **Hostname.** `<name>.apps.<dns suffix>`, always. The app writes `${app_host}` as its Ingress host; the app's Kustomization fills it. Certificate `wildcard-apps` (`*.apps.<dns suffix>`, internal CA) serves every app, so no app has its own certificate and none can claim a core or add-on name.
- **What core derives, per listed app** (`app/`, applied as the platform account by the env's `app-<name>-wiring`):
  - Namespace `app-<name>`, labelled `hosting.jarvis.io/app: <name>`, annotated with its host, the env, the env's pod, service and LAN ranges (`hosting.jarvis.io/lan-cidrs`) and the env's exception lines for the app, each `hosting.jarvis.io/<grant>`: `privileged`, `root`, `host-network`, `host-path`, `hostnames`, `lan-ports`, `lan-all`, `lan-targets` as `<name> <cidr> <port>/<protocol>` lines joined by commas, `no-uptime-check`; Pod Security `warn` and `audit` at `restricted`. No tenant can edit a Namespace: `app-tenant` refuses the kind, and the tenant Role does not grant it;
  - tenant account `flux-system/app-<name>` and Role `app` in `app-<name>` on the kinds an app ships;
  - NetworkPolicies `default-deny`, `same-namespace` and `cluster-dns`, and LimitRange `app` (per container: default limits 100m and 128Mi, default requests 50m and 128Mi); `default-deny` keeps `prune: disabled`, so a namespace the env drops stays isolated;
  - two sources reading only `<name>/app.yaml` and `<name>/deploy/`, and two tenant Kustomizations, `app-<name>-file` and `app-<name>` (which waits on the first), targeting `app-<name>`.
- **What core derives from the App** (ClusterPolicy `app-derive`, `policies/derive.yaml`): ResourceQuota `app` from `resources` (with the env's override), `services.nodeports: 0` and `services.loadbalancers` up to the number of `network.ports`; NetworkPolicies, each only when the App asks for it:
  - `app-web`: Traefik to `network.web.port`;
  - `app-ports`: from any address to the `target` of each `network.ports` entry the env grants as `lan-port <listen>/<protocol>`; an ungranted entry opens nothing. The source stays any address because ServiceLB rewrites it (its hostPort path arrives from its own pod in `kube-system`; kube-proxy's path is masqueraded, on a multi-node cluster to the forwarding node's address inside the pod range). Other apps' pods stay out on their own side: each app namespace denies egress by default, and no allow here reaches the pod range except `app-apps` peers. An app the env grants `lan-all`, or a `lan-target` range holding a node, still reaches the port through a node's LAN address, as any LAN device does (Limits);
  - `app-internet`: any port and protocol to `0.0.0.0/0` except RFC 1918, `100.64.0.0/10`, link-local, and the env's pod, service and LAN ranges (DNS comes from `cluster-dns`), with the env's override;
  - `app-lan-all`: any port to each of the env's LAN ranges, only when the App asks `lan: [all]` **and** the env grants `lan-all`;
  - `app-lan`: for each target the App lists under `egress.lan` **and** the env grants as `lan-target`, its range on the granted ports only;
  - `app-apps` (egress to the namespaces of `egress.apps`) and `app-callers` (ingress from the namespaces of `callers`): one side each, so traffic flows only when both list each other;
  - `app-backups` (egress to `restic-apps.platform-backups:8000/TCP`) exists only while the env registers the app's backup credential.
- **Memory containment.** Every app container's memory request equals its memory limit (`app-file`; a limit alone is fine, since Kubernetes copies it to the request; LimitRange `app` gives 128Mi for both). An app therefore reserves all it may use and never uses more of a node than the scheduler set aside for it. A container that passes its limit is OOM-killed in its own cgroup and restarted; no other pod is touched. This is per container, not a total app cap.
- **Lowest priority.** PriorityClass `hosted-app` (`priority.yaml`, value `-1000`, `preemptionPolicy: Never`), below every core and add-on pod (they set no class and run at 0; k3s's own run at `system-cluster-critical`). A core pod that cannot fit preempts app pods; an app pod never preempts anything, and stays Pending. Under node memory pressure the kubelet ranks pods whose usage exceeds their requests first and only then goes by priority, so priority puts apps first only among pods ranked alike: when system daemons overrun their reservations with every pod within requests, apps go first. ClusterPolicy `app-priority` sets it on every Deployment, StatefulSet, Job and CronJob in an `app-` namespace at admission, over any class the app picks; it ignores Kyverno failures (`failurePolicy: Ignore`) so core requests never wait on it, and `app-file` refuses a pod or workload at any other class, so without the mutation an app's workloads are refused rather than run at core's priority. The VolSync controller's movers keep core's priority. The node memory reserve that eviction protects is core's `node_memory_reserve_percent` ([schema/CONTRACT.md](../../schema/CONTRACT.md)).
- **Uptime.** The uptime check of `https://<name>.apps.<dns suffix>` is on for every app with `network.web`, wherever observability is on; it reads the App's `network.web.healthPath` and the namespace's `hosting.jarvis.io/no-uptime-check`, which is `true` only with the env's `<app>: no-uptime-check` line. The check itself is not built yet ([platform/traefik/CONTRACT.md](../traefik/CONTRACT.md)).
- **Admission** (`policies/admission.yaml`, native ValidatingAdmissionPolicies, `failurePolicy: Fail`):
  - `app-identity`: a namespace is named `app-<name>` exactly when it carries `hosting.jarvis.io/app: <name>`; an App lives only in its own namespace, named after it.
  - `app-tenant`: the tenant account writes only in `app-<name>`, and only ConfigMaps, Secrets, Services, PVCs, Deployments, StatefulSets, Jobs, CronJobs, Ingresses, PodDisruptionBudgets, HorizontalPodAutoscalers and its App. No Traefik CRD, NetworkPolicy, quota, RBAC, Flux, VolSync, DaemonSet or cluster-scoped object.
  - `app-file` and `app-grants`, each with one cluster-wide binding on every namespace labelled `hosting.jarvis.io/app`: the **pod baseline**, Pod Security `restricted` (no privileged mode, sysctls, host PID or IPC, host network or host ports, hostPath, or root; every container sets `allowPrivilegeEscalation: false`, drops `ALL` capabilities and adds back none but `NET_BIND_SERVICE`, has a `RuntimeDefault` or `Localhost` seccomp profile of its own or from the pod, no `procMount: Unmasked`, no unconfined AppArmor profile or annotation, no SELinux user, role or type beyond the container types, and runs `runAsNonRoot: true` with no `runAsUser: 0`; volumes only configMap, secret, emptyDir, PVC, projected, downwardAPI, csi or ephemeral, since a network volume mounts past every NetworkPolicy; anything beyond goes through the `privileged`, `root`, `host-network` and `host-path` exceptions), every pod at PriorityClass `hosted-app`, every container's memory request equal to its limit (or a limit alone), PVCs the StatefulSet controller names `<volume>-<set>-<n>` from a declared claim template, checked on Pods and on every workload template; every PVC and StatefulSet claim template is a declared volume, with `backup: none` exactly when declared `backup: false`, and sets no `volumeName`, `dataSource` or `dataSourceRef` (the volume binder's `volumeName` on bind passes, and so does an unchanged one after); Ingress host `<name>.apps.<dns suffix>`, `ingressClassName: traefik`, of Traefik's and other ingress controllers' annotations only `router.entrypoints: websecure` and `router.tls: "true"` (any other annotation passes), no default backend, no `spec.tls`; no Traefik annotation on a Service; Services ClusterIP, or LoadBalancer only on `network.ports` (each port a `listen` with its `protocol`, and a numeric `targetPort` equal to its `target`) and with `allocateLoadBalancerNodePorts: false` (ServiceLB needs no node port); no NodePort, ExternalName or `externalIPs`. `app-file` holds each object to the App in its own namespace; `app-grants` holds it to the env's grants, read from the namespace's annotations. A risky item, a custom hostname or a LAN port passes only when the App asks for it **and** the env grants it. A labelled namespace with no App refuses everything `app-file` matches, and a missing annotation grants nothing.
  - **The VolSync carve-out** is keyed on identities a tenant cannot take: Jobs and claims the VolSync controller (`volsync/volsync`) creates, and Pods the job controller creates for a Job. A tenant's own Job is checked when the tenant creates it, so a look-alike Job or Pod is refused. The scheduler's PreBind UPDATE (kubernetes v1.36.5 binder.go:450→565, adds `volume.kubernetes.io/selected-node` on WaitForFirstConsumer PVCs) and binder/controller-manager UPDATE (sets `volumeName`) of a VolSync-owned PVC (one with an ownerReference to a ReplicationSource or ReplicationDestination) pass even when the PVC is not declared in the App: VolSync cache claims, which the controller creates but the scheduler and binder provision, are not tenant-editable volumes. The carve-out requires UPDATE operation and VolSync provenance; CREATE is blocked.
- **Exceptions.** The only grants: `privileged`, `root`, `host-network`, `host-path`, `hostname <name>`, `lan-port <port>/<TCP|UDP>`, `lan-all`, `lan-target <name> <cidr> <port>/<TCP|UDP>` (one line per port; the range inside the env's `lan_cidrs`, the name a DNS label other than `all`), and `no-uptime-check`. There is no blanket grant. `lan-all` and `lan-target` need the env's `lan_cidrs` ([schema/CONTRACT.md](../../schema/CONTRACT.md)). LAN addresses live only in the env's repository, never in the apps repository.

## Expects

- The apps repository at `apps_git_repo_url` (https, readable without a credential), branch `main`, one folder per app: `<name>/app.yaml` and `<name>/deploy/` (plain manifests, or a kustomization). Other files in the folder never reach the cluster.
- The app's objects meet the rules above. `${app_host}` is the only variable they may use. The image and the probes are the app's own concern.
- The env lists the app in `envs/<env>/values/apps.yaml` (names only) and commits the render, `envs/<env>/flux/generated/apps.yaml`, listed in its `flux/kustomization.yaml`.
- An app with a `backup: true` volume has its own backup credential registered by the env ([platform/backups/CONTRACT.md](../backups/CONTRACT.md), App credentials); until then that PVC gets no backup and `make verify` fails it.
- **Tenant secrets.** No app secrets path exists yet. When one is built, it applies only Secrets sealed for the app, and never `backups-restic-app-<name>.sops.yaml`, which lives in the same `envs/<env>/secrets/app-<name>/` folder but is the backup credential `platform-backups` holds.
- Platform: the switch (`kustomization.yaml`) on the env's `platform-configs` path, which brings the CRD (`crd/`), the policies (`policies/`), PriorityClass `hosted-app` and ClusterPolicy `app-priority` (`priority.yaml`), Kyverno's aggregated role `kyverno:app-derive` (`kyverno-rbac.yaml`) and `wildcard-apps` (`certificate.yaml`); Kyverno and cert-manager from `platform-controllers`; Traefik in `kube-system` (`app.kubernetes.io/name: traefik`).

## Health

- The env's `app-<name>-wiring`, `app-<name>-file` and `app-<name>` Kustomizations are Ready; `make verify` waits on every Kustomization, so an app listed with no valid app file (`app-<name>-file` not Ready, `app-<name>` waiting) fails it.
- `make verify` component `apps` (only for an env that lists an app): bindings `app-file` and `app-grants` exist; each listed app's namespace carries its label, `default-deny`, `cluster-dns`, `same-namespace` and LimitRange `app`; its annotations hold exactly the env's exception lines; every Ingress host in it is `<name>.apps.<dns suffix>` or a granted hostname. An app PVC its App declares `backup: false` is reported as declared, not failed; `backup: none` on any other app PVC fails. An `app-` namespace the env no longer lists is reported.

## Config

- **Turn app hosting on:** the `components:` line above. The first time, `platform-configs` may fail one apply while the new App CRD becomes known to the API server and Kyverno; its next retry, about a minute later, passes with no action. An env that already ran apps before the `restricted`, `hosted-app` and claim rules (none yet) recreates their workloads once: the controllers' updates of objects admitted earlier, such as an old ReplicaSet's scale-down, are refused, and a Job's template cannot take the class. Turn it off only once the env lists no app; the CRD and the app namespaces keep `prune: disabled` and stay until the operator deletes them.
- **Turn an app on:** with app hosting on, add its name to `apps:` in `envs/<env>/values/apps.yaml`, run `python3 tools/lib/render_apps.py --env <env> --output envs/<env>/flux/generated/apps.yaml`, and list `generated/apps.yaml` in `envs/<env>/flux/kustomization.yaml`. **Turn it off:** remove the name and re-render (or, with no app left, delete the file and its line). Changing an app needs no env edit. The render holds only the env's names, lines, `apps_git_repo_url` and CIDRs (pod, service and LAN), and the `quote` value the wiring uses to keep its annotations strings; a core change to the wiring reaches the env with no re-render, unless it needs a new value there, which env-schema then reports.
- **The env's LAN ranges:** `lan_cidrs` in `values/cluster-vars.yaml`, required once an exception line grants `lan-all` or `lan-target`. Internet egress never reaches them.
- **Exception lines** go under `exceptions:` in the same file, one `- <app>: <grant>` each. A grant counts only for an app on the list whose App asks for the same item (`no-uptime-check` alone needs no ask); removing the line and re-rendering removes the grant at the next admission. A custom hostname stays outside the env's `dns_suffix`. Only the env's repository can grant one: its file reaches the cluster as the namespace annotations the platform account applies, never through the apps repository, and a file in the app's own folder grants nothing.
- **Per-env differences** live in the App's `spec.envs.<env>`.
- `tools/app-check <folder>...` is the validator the apps repository's CI runs, from a checkout of this repository at a pinned commit (Python 3, PyYAML, and kustomize for a `deploy/kustomization.yaml`).

## Operations

- **Remove an app for good:** [docs/add-a-hosted-app.md](../../docs/add-a-hosted-app.md#turn-it-off). Until the operator deletes the namespace, the cluster-wide bindings refuse every new pod in it, because its App is gone.
- **An env that ran apps on per-app bindings** keeps, with `prune: disabled`, bindings `app-file-<name>` and `app-grants-<name>` and ConfigMap `flux-system/app-<name>-grants`. Nothing reads them and they change no answer: `app-grants` has no params now, so the API server ignores the old `paramRef`. Delete them once, as the cluster admin, after the wiring has written the new annotations. Such an env also re-renders its `generated/apps.yaml` once, for `quote`.

## Limits

- A custom hostname's TLS is not served by the apps wildcard; a granted custom hostname gets Traefik's default certificate.
- Kyverno generates the quota and the derived NetworkPolicies after admission. Until it has, the app has the baseline's deny, and no namespace total (each container still has the LimitRange defaults).
- The live network-policy test runs once an env hosts an app.
- Movers in app namespaces stay privileged.
- Memory on a shared node is contained, not guaranteed. Apps cannot use more than they reserved, so node memory pressure comes from core or system pods growing past their own requests. In that case the kubelet evicts the pod over its requests, which can be a core pod while app pods within their requests stay. A spike faster than the kubelet's polling reaches the kernel's OOM killer, which picks by QoS and request size, not priority. There is no absolute promise that apps cannot be part of a core OOM, nor that core survives its own growth.
- Removing an exception line refuses only new objects. Pods already running, and pods the job controller makes for a Job admitted before, keep what the grant gave them until they are replaced.
- Admission holds an app namespace through its label. `app-identity` refuses a namespace named `app-<name>` without it, and only a cluster admin can take it off.
- Kyverno re-derives an app's allows when its App changes, not when the env's grants or ranges change: removing a `lan-all` or `lan-target` line updates the namespace and the grants at once, and closes the derived `app-lan-all` or `app-lan` at the App's next change. Until then the hole the App asked for and the env had granted stays open.
- Egress is filtered by address and port, not by internet hostname.
- No multicast, mDNS or other LAN discovery: a LAN target is a fixed range the env names.
- No internet-facing app: the web address and LAN ports are for the LAN.
- LAN ranges are IPv4 inside RFC 1918.
- The cluster's own nodes sit on the LAN: `lan-all`, or a `lan-target` range holding a node, lets the app's pods reach the node-side endpoints (the Kubernetes API, the kubelet, Traefik and anything else listening on a node) as any LAN device can. Grant the whole LAN only to an app trusted that far, and keep `lan-target` ranges off the nodes.
