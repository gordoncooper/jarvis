# CI

`ci/run-checks` runs every check listed in `ci/rule-checks.txt` and reports each one that fails. Any failure makes the run fail. `ci/tests/` holds the pytest suite. CI runs both once. Core holds no env: the tests and the env-level rule checks run on a sample instance written by `jarvis init`'s own code (`ci/tests/sample.py`), so they check exactly what a new env is.

Run `bash ci/run-checks` and the tests near your change before pushing. CI at the head SHA is the test record.

CI picks the tests by the files a pull request changes (`ci/select-tests`): a docs-only PR runs the rule checks and no pytest; a Renovate PR (`renovate/*`) runs `make deps`, which downloads and checksums every pinned CLI, the rule checks, and only the tests that name its changed files, or every test when it cannot place one; any other PR, and every push to `main`, runs the whole suite.

CI runs the suite in two jobs side by side: `suite (checks)` (the rule checks, lint, and every test but the Ansible role proofs) and `suite (roles)` (the role proofs, `-m roles`: the files in `ROLE_PROOFS`, `ci/tests/conftest.py`, over half the suite's time). The `ci` job passes only when both do, and it is the check a merge waits on. Locally, `pytest -m roles` and `pytest -m "not roles"` run either half. pytest runs on every CPU (`pytest-xdist`, `-n auto` in `pytest.ini`). Each test gets its own `tmp_path`, so tests must not share a fixed path. `-n 0` runs serially, for a debugger or a single slow test.

The env-level checks (the ones that read `envs/<env>` through `INSTANCE`) live in `jarvis/env/validate.py`. `jarvis validate` runs them all on an instance, and the instance workflow runs that command for each env with the core tag it pins. Core's CI runs them all on the sample instance (`ci/checks/sample-instance`), and the three that also read core's own trees (`addons`, `manifest-lint`, `secret-scan`) on core itself, under the same names. `ENVS="<env> ..."` limits the schema check to those envs; `.sops.yaml` rules are still checked against every env folder.

Before a command that reads app files (validate, render, secrets, up, verify, drill, restore), the jarvis CLI checks out the instance's `apps_git_repo_url` at its default branch with every tag (`jarvis/apps/checkout.py`), since each env deploys and checks an app at its pinned tag (`versions:` in `values/apps.yaml`), logs the checked SHA, and sets `APPS_REPO` to it. It checks out nothing for a core-only instance, which needs no apps checkout, and refuses envs that read different apps repositories. Product CI never runs it; product tests use fixtures.

Tests that build a throwaway env copy refuse a tracked path in the repo. Where the temp dir must sit inside a worktree, point pytest at a git-ignored one: `pytest --basetemp=.scratch/tmp`.

## End to end

`.github/workflows/e2e.yml` brings up a real cluster from the commit under test: k3d (k3s in Docker, at the env's k3s release: core's unless the env overrides it), the flux-operator role applying the env's FluxInstance and `sync.yaml`, every Kustomization and HelmRelease Ready, the example hosted apps (`jarvis/kit/examples-apps.yaml`) running from the apps repository at the tags the env pins (each app's sources at its tag, its Deployments Available, and hello-web answering over HTTPS with notes reachable and lan-demo refused), then `jarvis verify --smoke` and `jarvis drill`. The env is a throwaway one written by `jarvis init`'s code with app hosting and no add-on (`ci/e2e/make-env`), with secrets sealed to an age key that lives only on the runner. Its root source is a temporary branch of this repository holding the commit and that env, and so is its core source, except on a pushed release tag, where core is the tag itself; the job deletes the branch. Two legs run in parallel, core with App DNS and without it (`cluster (app-dns on|off)`), and the `e2e` job passes when both do. It runs nightly, by hand, on every pull request and on every `v*` tag. Its `changes` job decides: a pull request that touches no platform, add-on, env, Flux-role, tool or schema code reports `e2e` as skipped, which branch protection counts as passing, so `e2e` can be a required check. A fork's pull request cannot push the branch, so it is skipped there too.

## Quickstart

`.github/workflows/quickstart.yml` runs [docs/quickstart.md](../docs/quickstart.md)'s commands as written, so the doc cannot drift from what works. `ci/quickstart/script` turns the doc's `bash` blocks into one script. It replaces the doc's "Your choices" with CI's own, which must set exactly the same variables (`test_quickstart.py`), and feeds `jarvis node prep` its answers in the doc's order. The `node` job's runner is both the controller and the node: it gets an SSH server, a login key and the name `node1.home.lan` first, as a fresh node would have, and runs every command through `jarvis up` and `jarvis verify --smoke`. The `controller (macos)` job runs the controller's half on macOS: install, `jarvis init`, `jarvis validate` and `jarvis render --check`. The release installed is the pushed tag on a `v*` tag run, otherwise a throwaway tag at the commit under test. The instance repository is a throwaway branch of this one, which Flux reads over https, and the `cleanup` job deletes both. The push in the Quickstart sends the instance's own CI caller (`.github/workflows/ci.yml`), which a workflow's token may not push. The `node` job therefore pushes with the token of a GitHub App made for it, which also makes that push run the instance's CI on the throwaway branch, as in a real instance repository. The App needs no webhook and two repository permissions, Contents and Workflows (read and write), and is installed on this repository only. Its client ID is the repository variable `QUICKSTART_CLIENT_ID`, and a private key it generated is the secret `QUICKSTART_PRIVATE_KEY`. Without them the `node` job fails at its first step and names them. It runs on every `v*` tag, nightly, by hand, and on a pull request that touches what the Quickstart runs. It is not a required check.

## Coding-agent deny lists

`.claude/settings.json` and `.cursor/cli.json` link to the agent kit's deny lists (`jarvis/kit/agents/`, [agents/README.md](../agents/README.md)), which hold the same short list, each in its client's own syntax: no commands that reach real hosts or a cluster (`ssh`, `scp`, `ansible` ad-hoc, `kubectl`, `helm`, `flux`, the jarvis commands that reach hosts, a cluster or secrets: `site`, `up`, `node`, `verify`, `drill`, `restore`, `secrets`, `age-key-check`), no secret decryption (`sops`, `age -d`) or reads of the age key, kubeconfigs and SSH keys, and no force-push or merge. They are a speed bump, not the guard: a coding agent never holds the age key, a kubeconfig or an SSH key. No check proves them; keep the two files in step by hand.

## Known weak spots

These are gaps a maintainer should know about when a change looks green.

- **Manifest schemas need the network.** `test_flux_entry.py` validates rendered manifests with kubeconform, which downloads the Kubernetes schemas, a public CRD catalog and the VolSync CRDs for the pinned chart version. A failed download fails the test. The rendered tree holds no ReplicationSource or ReplicationDestination, since the backup policy generates them, so only the seeded test exercises the VolSync schemas.
- **Flux's offline build is not the controller.** The env checks build each Kustomization with `flux build kustomization --dry-run`, which never reads the cluster: a `substituteFrom` source must be in the env's tree (a sealed Secret cannot be read offline and fails the check), and a Kustomization on another source (a hosted app's repository) is listed but not built.
- **The manifest checks read raw files.** `digest-pin`, `loadbalancer`, `manifest-lint` and `pvc-backup` scan YAML as written. A value that only appears after `kustomize build` (a patch, a generator) or inside a rendered HelmRelease is not seen.
- **`require_roots` is off by default in the library functions.** The four check scripts turn it on, and `test_manifest_roots.py` runs the scripts to prove it. A new caller of `load_documents` has to opt in.
- **The k3s role's `main.yml` is never run end to end.** It downloads a binary, writes under `/etc` and starts a service, which needs root and a network. Tests cover its parts: the templates, the join URL expression, the refuse guard, the mount drop-in, and the modes of the config files. A change to the order of tasks in `main.yml` is not caught.
- **The node token read is not run.** The `slurp` of the control plane's node token in `token.yml` needs a real k3s server. Only the name resolution and the URL are tested.
- **Host tools are faked.** Role tests put a fake `systemctl` or `findmnt` first on `PATH`. They prove the role reacts to the answers it is given, not that the real tools answer that way.
- **Renovate config is checked by regex only.** The tests run each manager's pattern against the files it targets. They do not run Renovate. Run `renovate-config-validator` after any edit to `renovate.json`.
- **Tests that need `sops`, `age-keygen`, `kustomize` or `ansible-playbook` skip when the tool is missing, except in CI, where a missing tool fails.** A green local run on a machine without them proves less than CI does.
- **`test_app_admission_apiserver.py` skips without its API server, except in CI.** It alone runs the hosted-app policies on a real `kube-apiserver`, which validates them as the kyverno CLI does not. `make deps` installs those binaries on Linux (`kube-apiserver` and `etcd` in `mise.toml`), so it runs locally there.
